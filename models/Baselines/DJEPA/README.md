# D-JEPA baseline

Loads the official pretrained [D-JEPA](https://arxiv.org/abs/2410.03755)
(*"Denoising with a Joint-Embedding Predictive Architecture"*, Chen et al.,
ICLR 2025) ImageNet generator and runs it as a **training-free restoration
baseline** inside this framework's usual `*_model.py` / config / eval
pipeline.

Config: `checkpoints/Baselines/DJEPA_base.yml`. Run:

```bash
python trainer.py -opt checkpoints/Baselines/DJEPA_base.yml -infer
```

There is nothing to train here (`DJEPA_model.optimize_parameters()` raises if
called) -- always run with `-infer` (`is_train: false`), which makes
`trainer.py` skip straight to `validation()`.

## Why this isn't a normal deblurring model

D-JEPA's released checkpoints are ImageNet class-/unconditional *generators*
(FID 2-3.4 on ImageNet-256, per the paper). They were never trained to take a
degraded image and restore it, and the upstream repo ships no such mode. To
still use it as a restoration baseline, `djepa_wrapper.py` adapts the model's
generation process with an **SDEdit-style partial-regeneration trick**:

- D-JEPA generates images by progressively *unmasking latent tokens*
  (MaskGIT-style: start from an all-masked canvas, run `num_iter` rounds each
  revealing more tokens, predicted by a small per-token diffusion head), not
  by denoising Gaussian noise over the whole image like standard diffusion
  models -- so there's no direct equivalent of SDEdit's "add noise to
  timestep `t`, denoise from there".
- The token-masking analogue: encode the degraded (LQ) image into the same
  VAE latent space, then start the unmasking trajectory *partway through*
  with the LQ image's own tokens already filled in at the positions the
  schedule would have "decided" by that point. Those positions are held
  fixed (never touched); the remaining masked positions are generated by the
  model as usual, informed by the fixed LQ context through attention.
- `val.djepa_strength` (0, 1] plays the same role as SDEdit's `strength`:
  near 0 passes the LQ through almost unchanged (mostly a VAE
  encode/decode), 1.0 discards it entirely and generates from scratch
  (equivalent to the original `DJEPA.sample_tokens`).

See `sdedit_sample_tokens()` in `djepa_wrapper.py` for the implementation.
Expect this baseline to hallucinate/reorganize fine detail rather than
sharpen it -- it's a natural-image-prior baseline, not a trained deblur
network. Treat it as a comparison point, not a strong competitor.

## Layout

```
models/Baselines/DJEPA/
├── DJEPA_model.py     # BaseModel adapter: feed_data / validate_step / logging+metrics
├── djepa_wrapper.py   # framework-agnostic: checkpoint/VAE resolution+download, SDEdit sampling, DJEPARestorer
├── djepa_lib/         # vendored upstream D-JEPA model code (unchanged except two bugfixes, see below)
├── LICENSE_D-JEPA      # upstream MIT license
└── README.md           # this file
```

`djepa_lib/` is vendored from
[github.com/D-JEPA/djepa-imagenet](https://github.com/D-JEPA/djepa-imagenet)
(commit `a7947d1`, MIT license, itself based on
[MAR](https://github.com/LTH14/mar)). Only two kinds of changes were made
relative to upstream:

1. **Import paths**: upstream's internal imports are absolute (`from
   models.block import ...`), which would collide with this repo's own
   top-level `models` package. Rewritten to relative imports
   (`from .block import ...`); no logic changed.
2. **Two upstream bugs fixed** in `djepa_lib/djepa.py`, found by actually
   running inference against the released checkpoint (both break *any* use
   of the model, not just this baseline -- worth upstreaming):
   - `forward_encoder`/`forward_decoder` called `blk(x, freqs_cis=freqs_cis)`
     (`freqs_cis` always `None`), but `Block.forward` (`block.py`) only
     takes `x` -- raises `TypeError` as shipped. Fixed to `blk(x)`.
   - The released `.pth` checkpoints were saved from a `torch.compile`-wrapped
     model (the upstream training scripts pass `--compile`), so every
     state_dict key carries an `_orig_mod.` prefix. `load_djepa_weights()`
     strips it before `load_state_dict(..., strict=True)`.

## Pretrained weights

- **D-JEPA checkpoint**: auto-downloaded via `huggingface_hub` from
  [`densechen/d-jepa-imagenet`](https://huggingface.co/densechen/d-jepa-imagenet)
  (`djepa_{base,large,huge}.pth`, ~1.7GB / 5.5GB / 11.4GB). The EMA weights
  are used (`djepa_use_ema: true`), matching the paper's own `evaluate()`.
- **KL16 VAE checkpoint**: D-JEPA reuses [MAR](https://github.com/LTH14/mar)'s
  KL-16 VAE as-is (~266MB). It's Dropbox-hosted with no HF mirror, so it's
  fetched with a plain HTTP download to `djepa_cache_dir`
  (default `~/.cache/djepa/kl16.ckpt`).

Gilbreth compute nodes typically have no internet access -- either run once
on a login node to warm both caches, or pre-download both files and point
`djepa_checkpoint_path` / `djepa_vae_ckpt_path` in the config at local
copies.

## Config knobs

See the comments in `checkpoints/Baselines/DJEPA_base.yml`. Structural
choices baked into `djepa_wrapper.py` (`qk_norm=True`, `diffloss="gauss"`,
`jepaloss="jepa"`, `patch_size=1`, `vae_stride=16`) are **not** exposed as
config -- they must match how the released checkpoints were trained or
`load_state_dict(strict=True)` fails. Everything under `val.djepa_*` is a
free inference-time hyperparameter.

## Verification

This was smoke-tested end-to-end against the real `djepa_base` checkpoint
(not just unit-level): downloaded weights, `load_state_dict(strict=True)`
succeeded after the `torch.compile`-prefix fix, and `DJEPARestorer.restore()`
ran successfully on random tensors (square/non-square input, CFG on/off,
class-conditional, `strength` at both ends of its range) and on a real
blurry/sharp image pair from `images/gopro_000001_{blur,gt}.png`, producing
finite, structurally coherent (not NaN, not noise) [-1, 1] output images.
